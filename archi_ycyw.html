Proposition d'Architecture
Your Car Your Way

Ce document présente les choix architecturaux retenus pour la nouvelle plateforme web centralisée, en réponse aux déficiences systémiques identifiées dans l'audit technique et aux exigences du cahier des charges v2.0. L'architecture proposée est une refonte ex nihilo, capitalisant sur les bonnes pratiques de l'application US (containerisation, bcrypt, monitoring).

Section 01

Principes Directeurs de l'Architecture

Six principes fondamentaux guident l'ensemble des décisions d'architecture. Ils ne sont pas des aspirations — chacun répond à un problème structurel identifié et documenté dans l'audit technique.

🔌
API-First
Interopérabilité
Chaque fonctionnalité est d'abord exposée comme un endpoint API documenté (OpenAPI 3.0), avant d'être consommée par le frontend. Le contrat d'API devient la source de vérité partagée entre toutes les parties du système — frontend, applications agence, partenaires tiers.
Problème résolu : L'audit identifie l'absence totale d'API unifiée entre les 4 groupes d'applications. Les APIs existantes sont "limitées, hétérogènes et non unifiées entre pays".
☁️
Cloud-Native & Infrastructure as Code
Résilience
L'infrastructure est définie en code (Terraform), versionnée et reproductible. Les déploiements sont automatisés, la redondance est native (multi-AZ), et le scaling horizontal est déclenché automatiquement par les métriques de charge.
Problème résolu : Le groupe FR/DE/ES/IT opère sur OVH avec déploiements manuels, zéro redondance, et 21-28 min d'indisponibilité mensuelle. Taux de déploiements réussis : 82 %.
🔒
Security by Design
Conformité
La sécurité est intégrée à chaque couche de l'architecture, pas ajoutée après coup. Chaque service applique le principe du moindre privilège. Les secrets sont gérés par un vault centralisé. La surface d'attaque est minimisée par conception.
Problème résolu : SHA-1 sur FR/DE/ES/IT, TLS 1.0 actif sur FR et IT, secrets en fichiers de config, 41 % de vulnérabilités packages — risques critiques documentés dans l'audit.
♿
Accessibilité Universelle
WCAG 2.1 AA
L'accessibilité n'est pas un module optionnel — elle est un critère de qualité de sortie au même titre que les tests fonctionnels. Chaque composant frontend est conçu et testé (axe-core en CI) pour être conforme WCAG 2.1 niveau AA, couvrant les personas PSH du cahier des charges.
Problème résolu : Aucune des applications existantes ne documente de conformité WCAG. Le cahier des charges v2.0 l'exige contractuellement pour tous les marchés (WCAG 2.1 AA, Lighthouse ≥ 90).
⚖️
Stateless côté Applicatif
Scalabilité
Les services applicatifs ne conservent aucun état de session en mémoire locale. L'état est externalisé dans Redis. Cette propriété permet de multiplier les instances d'un service sans affecter la cohérence, et de les décommissionner sans perte de données utilisateur.
Problème résolu : Tous les monolithes existants ont une scalabilité uniquement verticale. La capacité maximale va de 150 req/s (FR) à 350 req/s (US) — insuffisante pour le trafic agrégé de 7 marchés.
🧩
Séparation Frontend / Backend
Maintenabilité
Le frontend (SPA React) et le backend (API REST) sont des artefacts de déploiement distincts, versionnés indépendamment. Cette séparation permet de faire évoluer l'expérience utilisateur et la logique métier à des rythmes différents, et de tester chaque couche de manière isolée.
Problème résolu : Les applications FR/DE/ES/IT utilisent JSP/JSF, qui couple étroitement rendu HTML et logique serveur. Le délai de stabilisation post-release atteint 3,4 jours — le plus élevé du portefeuille.
Section 02

Choix Technologiques Justifiés

Chaque choix technologique est motivé par les contraintes du cahier des charges, les enseignements de l'audit, et le critère de recrutabilité — la viabilité d'un choix technique dépend aussi de la disponibilité de compétences sur le marché.

Composant Choix retenu Alternative écartée Justification
FrontendReact 18 + TypeScript + Vite Retenu
Écarté Vue 3, Angular
 React est l'écosystème JS le plus mature pour les SPAs accessibles (librairies a11y, react-aria). Cohérent avec l'application Canada (déjà React) — base de compétences réutilisable. TypeScript + Vite garantit un DX rapide et une maintenabilité forte. Angular présente une courbe d'apprentissage trop élevée et reste associé dans l'audit à l'application US, jamais généralisée.
Backend — ServicesNode.js + NestJS + TypeScript Retenu
Écarté Spring Boot (Java)
 NestJS impose une architecture modulaire (modules, contrôleurs, services, guards) qui prévient la dérive vers un monolithe. Le partage du typage TypeScript avec le frontend réduit les erreurs d'intégration. Spring Boot, bien que robuste, est associé à Java EE — stack dont l'audit identifie la dépréciation et le déficit de recrutabilité sur le portefeuille existant.
Base de données principalePostgreSQL 16 (AWS RDS Multi-AZ) Retenu
Écarté MySQL, MongoDB
 PostgreSQL offre les transactions ACID nécessaires à la cohérence des réservations, le support natif de JSONB pour les données flexibles (options, horaires), et les extensions géospatiales (PostGIS) pour la recherche d'agences par position. RDS Multi-AZ répond directement à l'absence de redondance de base identifiée sur l'ensemble du portefeuille.
Cache & SessionsRedis 7 (AWS ElastiCache) Retenu
Écarté Memcached
 Redis remplit trois rôles : stockage des refresh tokens (TTL natif), cache des résultats de recherche fréquents (réduction de charge DB), et Pub/Sub pour le tchat temps réel entre instances de service. Memcached, plus simple, ne supporte pas le Pub/Sub ni les structures de données riches nécessaires au tchat.
Temps réel — TchatSocket.io + Redis Pub/Sub Retenu
Écarté RabbitMQ dédié, Firebase
 Socket.io assure la compatibilité WebSocket avec fallback long-polling pour les environnements restrictifs. Le Pub/Sub Redis synchronise les messages entre instances du service tchat, garantissant la livraison même avec plusieurs pods actifs. RabbitMQ ajouterait une dépendance d'infrastructure distincte non justifiée pour le seul cas d'usage du tchat.
AuthentificationJWT (RS256) + Refresh Token httpOnly Retenu
Écarté Sessions serveur
 JWT signé en RS256 (asymétrique) permet à chaque service de vérifier un token sans appel central — cohérent avec le principe Stateless. L'access token expire en 15 minutes ; le refresh token (7 jours, rotation à chaque usage) est stocké en cookie httpOnly pour bloquer les attaques XSS. Les sessions serveur centralisées seraient un point de couplage fort incompatible avec l'architecture distribuée.
PaiementStripe (Stripe Elements + Payment Intents) Retenu
— imposé par le CDC
 Stripe Elements garantit que les données de carte ne transitent jamais par les serveurs YCYW (conformité PCI-DSS SAQ A). L'API Payment Intents supporte nativement 3D Secure 2, les remboursements partiels et les webhooks de réconciliation. La conformité RGPD est facilitée par la tokenisation des moyens de paiement côté Stripe.
Hébergement / CloudAWS (eu-west-1 + us-east-1) Retenu
Écarté Azure, GCP
 AWS est déjà l'hébergeur des applications UK et Canada — l'équipe opérationnelle possède des compétences existantes réutilisables. EKS pour l'orchestration Kubernetes, RDS Multi-AZ pour la base de données, ElastiCache pour Redis, et CloudFront pour le CDN sont des services matures avec des SLA contractuels. Deux régions (EU et US) couvrent la latence des sept marchés cibles.
CI/CDGitHub Actions + ArgoCD Retenu
Écarté Jenkins, GitLab CI
 GitHub Actions s'intègre nativement avec les dépôts de code et offre un écosystème d'actions prêtes à l'emploi (test, lint, SAST, build Docker, push ECR). ArgoCD assure le déploiement continu via GitOps — l'état du cluster Kubernetes est déclaré dans Git et synchronisé automatiquement, éliminant les déploiements manuels responsables du taux d'échec de 18 % (FR/DE/ES/IT).
Conteneurisation & OrchestrationDocker + Kubernetes (AWS EKS) Retenu
Écarté AWS ECS, VM classiques
 La containerisation est la pratique identifiée comme la plus structurante de l'application US — la seule à atteindre 98,9 % de disponibilité. Kubernetes (EKS) permet le scaling horizontal automatique (HPA), les rolling deployments sans downtime, et la gestion déclarative des ressources. ECS serait une alternative viable mais Kubernetes offre une portabilité multi-cloud supérieure pour une future neutralisation du fournisseur.
Emails transactionnelsAmazon SES + React Email (templates) Retenu
Écarté SendGrid
 Amazon SES s'intègre nativement à l'écosystème AWS déjà retenu, avec un coût à l'usage très inférieur aux plateformes tiers à l'échelle. React Email permet de créer des templates responsive et accessibles en TypeScript, partageant le langage et les composants du frontend.

Description des flux principaux

Authentification : Le client soumet ses identifiants à l'API Gateway, qui les transmet au Service Utilisateur. Ce service vérifie le mot de passe contre le hash Argon2id en base, génère un access token JWT (RS256, TTL 15 min) et un refresh token opaque (TTL 7 jours) stocké en cookie httpOnly et persisté dans Redis avec révocation possible. Si le 2FA est activé, un code OTP est généré et envoyé via le Service Notification avant la délivrance des tokens.

Réservation : Le Service Réservation vérifie la disponibilité du véhicule (verrou optimiste en base pour prévenir la double réservation), crée un Payment Intent Stripe, et attend la confirmation de paiement via webhook Stripe. À la confirmation, la réservation passe au statut confirmed, le véhicule est marqué indisponible, et un événement est publié dans la queue interne. Le Service Notification consomme cet événement et déclenche l'email de confirmation via SES.

Tchat en temps réel : Le frontend établit une connexion WebSocket avec le Service Tchat (proxiée par l'API Gateway après vérification JWT). Chaque message entrant est persisté en base PostgreSQL et publié sur le canal Redis Pub/Sub de la session. Tous les pods du Service Tchat abonnés à ce canal diffusent le message aux connexions WebSocket concernées — garantissant la livraison même en présence de plusieurs instances actives.

Section 04

Modèle de Données — Schéma Relationnel

Le schéma relationnel est conçu pour PostgreSQL 16. Les clés primaires sont des UUID (gen_random_uuid()) pour éviter l'exposition d'identifiants séquentiels dans les URLs. Les index sont définis sur les colonnes fréquemment filtrées. Le soft-delete (champ deleted_at) est utilisé sur les users pour satisfaire le droit à l'oubli RGPD avec conservation des données comptables.

SQL — PostgreSQL 16 Schéma initial — CREATE TABLE + INDEX 
-- ═══════════════════════════════════════════════════════════════
-- YCYW — Schéma relationnel initial · PostgreSQL 16
-- ═══════════════════════════════════════════════════════════════

-- Extension UUID (disponible par défaut sur AWS RDS)
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- ─────────────────────────────────────────────────────────────
-- users : Profils des clients, agents et administrateurs.
-- Le soft-delete (deleted_at) permet la conformité RGPD :
-- suppression logique immédiate, purge physique différée.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE users (
  id               UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  email            VARCHAR(255)  NOT NULL UNIQUE,
  password_hash    VARCHAR(255)  NOT NULL,          -- Argon2id
  role             VARCHAR(20)   NOT NULL DEFAULT 'client'
                     CHECK (role IN ('client', 'agent', 'admin')),
  first_name       VARCHAR(100),
  last_name        VARCHAR(100),
  date_of_birth    DATE,
  phone            VARCHAR(30),
  locale           VARCHAR(10)   NOT NULL DEFAULT 'fr',  -- ex: 'fr', 'en', 'zh'
  currency         CHAR(3)       NOT NULL DEFAULT 'EUR', -- ISO 4217
  loyalty_points   INTEGER       NOT NULL DEFAULT 0,
  two_fa_enabled   BOOLEAN       NOT NULL DEFAULT FALSE,
  deleted_at       TIMESTAMP,                          -- soft-delete RGPD
  created_at       TIMESTAMP     NOT NULL DEFAULT NOW(),
  updated_at       TIMESTAMP     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_users_email      ON users(email);
CREATE INDEX idx_users_deleted_at  ON users(deleted_at) WHERE deleted_at IS NOT NULL;


-- ─────────────────────────────────────────────────────────────
-- agencies : Points de prise en charge et de retour des véhicules.
-- Le champ opening_hours est stocké en JSONB pour flexibilité.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE agencies (
  id             UUID           PRIMARY KEY DEFAULT gen_random_uuid(),
  name           VARCHAR(255)   NOT NULL,
  country        CHAR(2)        NOT NULL,           -- ISO 3166-1 alpha-2
  city           VARCHAR(100),
  address        TEXT,
  postal_code    VARCHAR(20),
  lat            DECIMAL(9,6),
  lng            DECIMAL(9,6),
  phone          VARCHAR(30),
  opening_hours  JSONB,         -- { "mon":"08:00-20:00", "tue":"08:00-20:00", ... }
  is_accessible  BOOLEAN        NOT NULL DEFAULT FALSE, -- accessibilité PMR
  active         BOOLEAN        NOT NULL DEFAULT TRUE,
  created_at     TIMESTAMP      NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_agencies_country  ON agencies(country);
CREATE INDEX idx_agencies_active   ON agencies(active) WHERE active = TRUE;
-- Index géospatial (requires PostGIS extension) :
-- CREATE INDEX idx_agencies_geo ON agencies USING GIST (ST_MakePoint(lng, lat));


-- ─────────────────────────────────────────────────────────────
-- vehicles : Parc de véhicules disponibles, classifiés ACRISS.
-- Le champ available est mis à jour transactionnellement lors
-- de chaque réservation pour prévenir les doublons.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE vehicles (
  id             UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  agency_id      UUID          NOT NULL REFERENCES agencies(id) ON DELETE RESTRICT,
  acriss_code    CHAR(4)       NOT NULL,     -- ex: CCAR, SWAR, FVMR
  category       VARCHAR(50),
  make           VARCHAR(50),
  model          VARCHAR(50),
  year           SMALLINT,
  seats          SMALLINT,
  transmission   VARCHAR(20)   CHECK (transmission IN ('manual', 'automatic')),
  fuel_type      VARCHAR(20)   CHECK (fuel_type IN ('petrol', 'diesel', 'electric', 'hybrid')),
  is_accessible  BOOLEAN       NOT NULL DEFAULT FALSE, -- véhicule adapté PMR
  available      BOOLEAN       NOT NULL DEFAULT TRUE,
  daily_rate     DECIMAL(10,2),
  currency       CHAR(3)       NOT NULL DEFAULT 'EUR',
  created_at     TIMESTAMP     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_vehicles_agency     ON vehicles(agency_id);
CREATE INDEX idx_vehicles_acriss     ON vehicles(acriss_code);
CREATE INDEX idx_vehicles_available  ON vehicles(available) WHERE available = TRUE;


-- ─────────────────────────────────────────────────────────────
-- reservations : Réservations de location créées par les clients.
-- Le champ options (JSONB) stocke les extras souscrits.
-- stripe_payment_intent_id garantit l'idempotence du paiement.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE reservations (
  id                        UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id                   UUID          NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  vehicle_id                UUID          NOT NULL REFERENCES vehicles(id) ON DELETE RESTRICT,
  pickup_agency_id          UUID          NOT NULL REFERENCES agencies(id) ON DELETE RESTRICT,
  return_agency_id          UUID          NOT NULL REFERENCES agencies(id) ON DELETE RESTRICT,
  start_date                TIMESTAMP     NOT NULL,
  end_date                  TIMESTAMP     NOT NULL,
  status                    VARCHAR(20)   NOT NULL DEFAULT 'pending'
                              CHECK (status IN ('pending','confirmed','modified','cancelled','completed')),
  stripe_payment_intent_id  VARCHAR(255)  UNIQUE,    -- idempotence paiement Stripe
  total_amount              DECIMAL(10,2) NOT NULL,
  currency                  CHAR(3)       NOT NULL DEFAULT 'EUR',
  options                   JSONB,                    -- { "gps":true, "child_seat":1, "insurance":"premium" }
  cancelled_at              TIMESTAMP,
  refund_amount             DECIMAL(10,2),
  created_at                TIMESTAMP     NOT NULL DEFAULT NOW(),
  updated_at                TIMESTAMP     NOT NULL DEFAULT NOW(),
  CONSTRAINT chk_dates CHECK (end_date > start_date)
);
CREATE INDEX idx_reservations_user     ON reservations(user_id);
CREATE INDEX idx_reservations_vehicle  ON reservations(vehicle_id);
CREATE INDEX idx_reservations_status   ON reservations(status);
CREATE INDEX idx_reservations_dates    ON reservations(start_date, end_date);


-- ─────────────────────────────────────────────────────────────
-- chat_sessions : Sessions de messagerie entre un client et le
-- service client. Peut être liée à une réservation spécifique.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE chat_sessions (
  id              UUID       PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  reservation_id  UUID       REFERENCES reservations(id) ON DELETE SET NULL,
  status          VARCHAR(20) NOT NULL DEFAULT 'open'
                    CHECK (status IN ('open', 'closed')),
  created_at      TIMESTAMP  NOT NULL DEFAULT NOW(),
  closed_at       TIMESTAMP
);
CREATE INDEX idx_chat_sessions_user         ON chat_sessions(user_id);
CREATE INDEX idx_chat_sessions_reservation  ON chat_sessions(reservation_id);
CREATE INDEX idx_chat_sessions_status       ON chat_sessions(status) WHERE status = 'open';


-- ─────────────────────────────────────────────────────────────
-- chat_messages : Messages individuels d'une session de tchat.
-- sender_role distingue client, agent humain et bot de support.
-- ─────────────────────────────────────────────────────────────
CREATE TABLE chat_messages (
  id           UUID       PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id   UUID       NOT NULL REFERENCES chat_sessions(id) ON DELETE CASCADE,
  sender_role  VARCHAR(20) NOT NULL
                 CHECK (sender_role IN ('client', 'agent', 'bot')),
  sender_id    UUID       REFERENCES users(id) ON DELETE SET NULL, -- NULL si bot
  content      TEXT       NOT NULL,
  sent_at      TIMESTAMP  NOT NULL DEFAULT NOW(),
  read_at      TIMESTAMP                      -- NULL = non lu
);
CREATE INDEX idx_chat_messages_session  ON chat_messages(session_id);
CREATE INDEX idx_chat_messages_sent_at  ON chat_messages(sent_at);
Section 05

Stratégie de Sécurité et Conformité

La stratégie de sécurité est construite en réponse directe aux défaillances identifiées dans l'audit. Elle couvre cinq domaines : authentification, gestion des secrets, transport, RGPD et conformité PCI-DSS.

A
Authentification et gestion des mots de passe

L'algorithme de hachage retenu est Argon2id (vainqueur de la Password Hashing Competition 2015, recommandation OWASP 2024), configuré avec un coût mémoire de 64 Mo, 3 itérations et 2 threads parallèles. Ce choix remplace directement SHA-1 (FR/DE/ES/IT) et bcrypt cost 10 (UK) identifiés dans l'audit.

La gestion des sessions repose sur deux tokens distincts. L'access token JWT (RS256) a une durée de vie de 15 minutes — limiter l'exposition en cas d'interception. Le refresh token est un token opaque de 64 octets aléatoires, TTL 7 jours, avec rotation à chaque usage (rotation détectée = révocation de la famille de tokens). Il est transmis exclusivement via cookie httpOnly + Secure + SameSite=Strict pour prévenir les attaques XSS.

Argon2id (64 Mo, 3 iter) JWT RS256 · TTL 15 min Refresh Token rotation httpOnly + SameSite=Strict Verrouillage 5 tentatives 2FA TOTP / SMS
B
Gestion des secrets

Aucun secret (clé API, mot de passe de base de données, clé de signature JWT) ne doit apparaître dans le code source, les fichiers de configuration versionnés, ou les images Docker. Cette règle est la première leçon tirée de l'audit : FR/DE/ES/IT stocke ses secrets dans des fichiers de configuration sur serveur — pratique inacceptable.

Les secrets sont gérés via AWS Secrets Manager, avec rotation automatique activée pour les credentials de base de données (tous les 30 jours). Les secrets sont injectés en variables d'environnement dans les conteneurs Kubernetes au moment du démarrage via des Kubernetes Secrets chiffrés à l'aide d'une clé KMS. Un scan de secrets (GitGuardian ou truffleHog) est intégré dans la pipeline CI pour rejeter tout commit contenant un secret détecté.

AWS Secrets Manager Rotation automatique (30 j) Kubernetes Secrets + KMS Scan CI (GitGuardian) Aucun secret dans le code
C
Conformité TLS

La version minimale de TLS autorisée est TLS 1.3 sur l'ensemble des points d'entrée publics (CloudFront, API Gateway, Load Balancer). TLS 1.2 est accepté en fallback uniquement pour les environnements d'intégration partenaires qui ne supportent pas encore TLS 1.3, avec une politique de dépréciation documentée à 18 mois. TLS 1.0 et TLS 1.1 sont explicitement désactivés — sans exception, en réponse directe à leur présence sur FR et IT dans l'audit.

Les certificats TLS sont gérés via AWS Certificate Manager (ACM) avec renouvellement automatique. L'en-tête HTTP Strict-Transport-Security (HSTS) est configuré avec max-age=31536000 et includeSubDomains.

TLS 1.3 minimum HSTS · max-age 1 an ACM · renouvellement auto TLS 1.0/1.1 désactivés
D
Conformité RGPD

Minimisation des données : Seuls les champs strictement nécessaires à chaque fonctionnalité sont collectés. Le numéro de carte bancaire n'est jamais collecté — il est saisi directement dans Stripe Elements côté navigateur.

Droit à l'oubli : La suppression de compte est implémentée en deux temps. Le soft-delete (deleted_at non null) est appliqué immédiatement — l'utilisateur perd l'accès instantanément. Une tâche planifiée (cron) évalue quotidiennement les comptes supprimés et effectue l'anonymisation physique (remplacement des données personnelles par des valeurs hachées ou nulles) à l'issue de la durée légale de conservation des données comptables (5 ans). Les données de réservation anonymisées sont conservées pour les obligations légales.

Consentement : Le bandeau cookies respecte la recommandation CNIL — pas de pré-cochage, pas d'action implicite valant consentement. Les préférences de consentement sont stockées avec leur horodatage et la version de la politique d'utilisation acceptée.

Soft-delete + anonymisation Export données (JSON/CSV) Consentement granulaire Registre des traitements DPO désigné
E
Conformité PCI-DSS (Paiement)

La conformité PCI-DSS est assurée par l'utilisation de Stripe Elements, qui isole complètement la saisie des données de carte dans un iframe hébergé par Stripe. Les données de carte ne transitent à aucun moment par les serveurs YCYW — le backend ne manipule que des objets Stripe (Payment Intent ID, Customer ID), jamais de PAN, CVV ou date d'expiration.

Ce choix positionne YCYW en niveau SAQ A de conformité PCI-DSS — la plus légère des auto-évaluations, applicable aux marchands dont les pages de paiement sont entièrement externalisées chez un tiers certifié (Stripe est certifié PCI-DSS niveau 1). Les remboursements sont initiés via l'API Stripe (jamais manuellement), assurant une piste d'audit complète. Les webhooks Stripe sont vérifiés par signature (Stripe-Signature header) pour prévenir les rejeux.

Stripe Elements (iframe) PCI-DSS SAQ A Aucun PAN/CVV côté backend Webhooks signés Remboursement via API
Section 06

Plan de Migration depuis l'Existant

La migration s'articule en trois phases séquentielles. L'objectif est de ne jamais interrompre le service existant pendant la transition, de garantir la conformité RGPD de chaque transfert de données, et de valider la nouvelle plateforme sur un marché pilote avant la généralisation.

1
Remédiation Urgente de l'Existant
À réaliser avant le début de la migration — parallèle au démarrage du projet
2 à 4 semaines

L'audit identifie des vulnérabilités critiques qui ne peuvent attendre la mise en production de la nouvelle plateforme. Cette phase traite les risques immédiats sur le parc existant sans attendre la refonte.

  • Migration SHA-1 → Argon2id (FR/DE/ES/IT) : Migrer les hashs de mots de passe de façon transparente. Le nouveau hash Argon2id est calculé à la prochaine connexion réussie de chaque utilisateur (migration lazy). Un batch nocturne force une réinitialisation de mot de passe pour les comptes inactifs depuis plus de 6 mois.
  • Désactivation de TLS 1.0 et TLS 1.1 (FR et IT) : Mise à jour de la configuration des serveurs OVH concernés. Test de compatibilité préalable avec les partenaires d'intégration. Application du protocole TLS 1.2 minimum en attendant la migration vers TLS 1.3 sur la nouvelle plateforme.
  • Rotation des secrets applicatifs : Renouvellement de toutes les clés API, credentials de base de données et tokens d'intégration sur FR/DE/ES/IT. Migration des secrets vers des variables d'environnement (au minimum) ou AWS Secrets Manager si l'infrastructure le permet. Révocation des anciens secrets après transition.
  • Audit et patch des vulnérabilités packages : Exécution d'un audit de dépendances (OWASP Dependency-Check) sur les quatre groupes. Mise à jour prioritaire des bibliothèques présentant des CVE critiques ou élevées — en particulier les 41 % de packages vulnérables identifiés sur FR.
2
Déploiement Parallèle avec Marché Pilote
Nouvelle plateforme en production — l'existant reste actif en parallèle
3 à 6 mois

La nouvelle plateforme est développée, testée et déployée en production sur un marché pilote unique, pendant que l'ensemble du parc existant continue d'opérer normalement.

  • Sélection du marché pilote : Le Royaume-Uni est recommandé — application PHP Laravel la plus récente du portefeuille continental, modèle de données moins divergent, équipe opérationnelle familière avec AWS. L'application UK est la mieux positionnée pour une migration de données initiale.
  • Développement de la nouvelle plateforme : Développement par cycles de deux semaines (sprints), en suivant les 27 user stories du cahier des charges v2.0 priorisées MoSCoW. Les fonctionnalités Must Have (authentification, recherche, réservation, paiement) sont livrées en priorité.
  • Feature flags par pays : Un système de feature flags (ex. LaunchDarkly ou Unleash) permet d'activer progressivement des fonctionnalités pour le marché pilote sans affecter les autres marchés. La nouvelle plateforme est déployée derrière un flag market=UK — les utilisateurs UK sont redirigés vers la nouvelle URL, les autres marchés continuent sur l'ancien système.
  • Migration des données UK : ETL (Extract, Transform, Load) de la base de données UK vers le schéma unifié PostgreSQL. Validation de la qualité des données migrées (tests d'intégrité référentielle, réconciliation des comptes actifs). Conformité RGPD de la migration documentée (finalité, base légale, durée de conservation).
  • Validation et stabilisation : Période d'exploitation parallèle d'au minimum 4 semaines sur le marché pilote. Suivi des KPIs cibles (disponibilité ≥ 99,9 %, taux d'erreur < 0,5 %, MTTR < 30 min). Revue de sécurité (pentest externe) avant passage à la phase 3.
3
Bascule Progressive et Décommissionnement
Généralisation pays par pays — décommissionnement progressif des anciens systèmes
6 à 12 mois

Fort des enseignements du marché pilote, la bascule est déployée séquentiellement sur les marchés restants, dans un ordre priorisé par le rapport risque/effort de migration des données.

  • Ordre de bascule recommandé : Canada (stack Node.js/React, familiarité AWS, modèle de données relativement proche), puis États-Unis (containerisé, bien documenté), puis Italie, Espagne, Allemagne, et France en dernier (marché le plus complexe, dette technique la plus élevée, base utilisateurs la plus volumineuse).
  • Migration des données par pays : Pour chaque marché, une fenêtre de maintenance planifiée (nuit creuse) est utilisée pour le cut-over de la base de données. Les utilisateurs sont notifiés 48h à l'avance. La migration respecte la conformité RGPD : les données sont transférées sans changer de responsable de traitement (même entité juridique YCYW), la finalité reste identique — aucun nouveau consentement n'est requis, mais les utilisateurs sont informés (obligation d'information Art. 14 RGPD).
  • Migration des mots de passe : Les hashs Argon2id (déjà migrés en Phase 1 pour FR/DE/ES/IT) sont importés directement. Les anciens hashs bcrypt (UK, US) sont conservés et re-hashés à la première connexion via le mécanisme de migration lazy (validation du hash ancien, recalcul en Argon2id).
  • Décommissionnement progressif : Après 30 jours de stabilisation sur la nouvelle plateforme, les anciennes applications sont mises en mode lecture seule (lecture des réservations historiques uniquement), puis décommissionnées définitivement après 90 jours. Les serveurs OVH sont restitués. Les bases de données archivées sont conservées chiffrées pendant 5 ans (obligations légales) puis purgées.
  • Validation RGPD finale : Mise à jour du registre des traitements, révision des DPA (Data Processing Agreements) avec les sous-traitants, audit de conformité par le DPO, et clôture du projet avec rapport d'audit final documentant la chaîne de traitement des données tout au long de la migration.
Points de vigilance transverses

La migration représente une période de risque opérationnel élevé. Deux pratiques sont non négociables : aucun cut-over sans rollback testé (chaque migration doit avoir un plan de retour à l'ancien système en moins de 2 heures), et aucune migration de données sans audit RGPD préalable (chaque lot de données migré doit avoir une base légale documentée et un responsable désigné).

La durée totale estimée de la migration — phases 2 et 3 confondues — est de 9 à 18 mois selon les ressources mobilisées et les aléas rencontrés en Phase 3. Cette estimation ne prend pas en compte la Phase 1 (remédiation urgente), qui doit démarrer immédiatement et de manière indépendante.
